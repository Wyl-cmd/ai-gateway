# 落地总表 —— 施工顺序（按父先子后）

> **铁律**：每批走四道门 —— ① 方案（本节六要素）→ ② 测试必红（`AssertionError`/`KeyError`，
> 不是 `NameError`）→ ③ 最小改动转绿 → ④ 全量回归。
>
> **父→子判据**：A 是 B 的父 ⟺ **B 做完立刻跑一遍必须依赖 A 已成立**。
> 不是按章节顺序，不是按域。

---

## 依赖图

```
G0 骨架 ──→ G1 数据层 ──→ G2 转发层 ──┬──→ G3 路由层 ──┬──→ G7 模式层 ──→ G8 接入层 ──→ G10 端到端
                                      │                │
                                      └──→ G4 破甲层 ──┘

G6 可观测（route_trace + token 计量）横切 G3/G4，最后接线
（原 G5 压缩层已删除）
G9 CLI 挂在最后
```

**为什么 G2 转发层这么早**：所有层最终都要「发一次请求」才能验证。
没有转发层，破甲层没法测（改了 prompt 发给谁？）、路由层没法测（选了谁去调？）。

## G2 转发层（最底层，5 家 provider）  ✅ **已完成（commit `e026a9b`）**

| 验收项 | 结果 |
|---|---|
| 门② 必红 | `ModuleNotFoundError: No module named 'gateway.providers'` ✅ |
| 门③ 转绿 | 25 passed / exit=0 ✅ |
| 门④ 回归 | 34 passed / exit=0（9 G0/G1 + 25 G2）✅ |
| 源文件 | `providers/{base,openai,anthropic,deepseek,gemini,aggregator,__init__}.py` 共 7 个 / 410 行 |

**门③ 实测撞到的坑（已修正）**：第一版 `parse_sse` 每次调用先 `self._sse_buf = b""`，
导致「一块被切成两半」的数据接不上 —— `parse_sse(part1) + parse_sse(part2)` 返回空。
**测试口径是对的，实现是错的**：流式解析必须跨调用保留缓冲。删掉那一行即转绿。

**落地时对设计的两处修正**：
1. `_QUOTA_MARKERS` 除了 freellmpool 的 6 条英文，按国内厂商补了 5 条中文
   （余额不足 / 额度已用尽 / 配额已用尽 / 账户欠费 / 已超出套餐）——
   我们要接 DeepSeek/Qwen 这些中文厂商，只有英文文案识别不出来。
2. `classify_failure` 先判 quota 再判 health。**顺序不能反**：配额耗尽的
   状态码是 429（按状态码本该算 health），但它的处理方式是「只跳账号」而不是
   「跳整个 provider」—— 先判 health 会把它吞掉，三层降级的第二层就塌了。

| 项 | 内容 |
|---|---|
| **改哪个文件** | 新建 `src/gateway/providers/{base,openai,anthropic,deepseek,gemini,aggregator}.py` |
| **不改** | 不动 `storage/`、`config.py` 的既有字段 |
| **怎么改** | 抄 one-api `relay/adaptor/interface.go` 的契约：`Adaptor` 抽象类定义 `chat()` / `stream()` / `models()` / `transform_request()` / `transform_response()`。5 家各实现自己的字段映射 |
| **测试怎么写** | `test_providers.py`（**不发真请求**，用 `httpx.MockTransport`）：① 各家 `transform_request` 把统一格式转成自家格式 ② `transform_response` 反向 ③ 流式 `parse_sse()` 逐块解析正确 ④ 上游 4xx/5xx 被包成统一的 `ProviderError`（带 `is_health_failure` 标记） |
| **红的判定** | `ImportError` / `AttributeError`（`Adaptor` 未定义） |
| **验收命令** | `.venv/bin/python -m pytest tests/test_providers.py -q` |

**关键**：`ProviderError` 必须带 `is_health_failure` 和 `is_quota_exhausted` 两个布尔标记
（抄 freellmpool 的 `_is_health_failure` / `_is_account_quota_exhaustion`）——
这是 G3 路由层做失败分类的唯一输入。

## 执行顺序建议（最短验证路径）

```
G0 → G1 → G2
   → G4-J4（拒绝检测，纯函数，零依赖最快见效）
   → G3（路由）
   → G4-J1 → J2 → J3（破甲主体）
   → G6（可观测接线）
   → G7（模式层）
   → G8（接入层，第一次能真跑）
   → G9（CLI）
   → G4-J5 → J6 → J7（破甲进阶）
   → G10（端到端）
```

**关键里程点**：**G8 完成 = 第一次能真跑通一次请求**。之前的 8 批都是「零件」，G8 才把零件装成机器。
