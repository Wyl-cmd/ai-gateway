## 一、one-api（管理面）

### ✅ 借什么

| 机制 | 落点 | 为什么值得借 |
|---|---|---|
| **渠道抽象**（`relay/adaptor/` 38 个 provider 适配器 + `interface.go` 统一接口） | 我们的 `providers/` 层 | 38 家已验证的字段差异，自己重新踩一遍这些坑不划算 |
| **能力表**（`model/ability.go`） | 路由决策的输入 | 「哪个渠道能服务哪个模型」用表查而不是硬编码 if/else，这是路由的前提 |
| **令牌与配额分离**（`model/token.go` / `model/channel.go`） | 鉴权层 | 用户令牌和上游密钥是两回事，混一起会导致「一个用户泄露=所有渠道泄露」 |
| **额度与日志**（`model/log.go` / `model/redemption.go`） | 计量层 | 按 token 计费 + 兑换码，是运营必需，不是可选 |
| **relaymode**（`relay/relaymode/`） | 协议分发 | chat / embedding / image / audio 走不同的处理链，先分流再适配 |

### ❌ 弃什么

| 不借 | 理由 |
|---|---|
| **Vue 前端（`web/` 242 个 js）** | 我们要的是网关，不是又一个管理后台。前端另起轻量方案，不搬 242 个文件 |
| **Go + GORM 全家桶** | 技术栈待定（见架构文档「技术栈决策」），不为此绑死 Go |
| **单体 main.go 启动模式** | 38 个 adaptor 全注册在启动时，冷启动慢；我们按需加载 |
| **`model/cache.go` 的进程内缓存** | 多实例部署时各自缓存会不一致，改用共享缓存（或先做单实例再说，但不假装支持多实例） |

## 二、freellmpool（路由决策）

### ✅ 借什么

| 机制 | 落点 | 为什么值得借 |
|---|---|---|
| **健康租约**（`router.py: _acquire_route` / `_record_route_success` / `_record_route_failure` / `_refresh_route_lease`） | 路由健康层 | 这不是简单的「成功+1 失败-1」，是带租约的并发控制，防同一死路由被多请求同时打 |
| **失败分类**（`_is_health_failure` / `_health_failure_class` / `_is_account_quota_exhaustion`） | 熔断判据 | **配额耗尽 ≠ 服务故障**。前者应换账号，后者应换 provider。混为一谈会导致「换个 key 继续撞墙」 |
| **目标排序**（`rank_targets`） | 路由决策核心 | 综合健康度 + 配额 + 延迟排序，而不是「按优先级列表硬试」 |
| **冷却快照**（`cooldown_snapshot` / `route_health_snapshot` / `conformance_snapshot`） | 可观测层 | 出问题时能回答「为什么走了这条路由」，不是靠猜 |
| **第一波分离**（`_provider_first_wave`） | 降级策略 | 先打「主力池」，失败才降到「免费/备用池」——避免每次都从免费池开始试 |
| **SERVICE-INVENTORY.md 这份清单本身** | 我们的文档规范 | 「每个服务一行：文件 / 职责 / 关键方法」，防重复造轮子。这个习惯直接抄 |

### ❌ 弃什么

| 不借 | 理由 |
|---|---|
| **「keyless 启动」** | 上游卖点是「没有密钥也能开始用」。我们的场景不需要，且 keyless 端点稳定性无保障 |
| **`tokenmax` 的 fan-out 合成** | 一次请求打多个模型再合成答案 —— 成本和延迟翻倍，且合成质量不可控。**不做** |
| **MCP server 那一层** | 上游把网关包装成 MCP 工具。我们直接暴露 HTTP，MCP 需要时另说 |
| **`roles.py` 的角色预设** | 上游用 CLI 角色映射到路由参数。我们的路由参数由请求内容和策略决定，不靠用户选角色 |
| **本地 JSONL job queue** | 单机方案。我们若要多实例就不适用；先不做队列，需要时用真队列 |

## 三、9router（SSE 分层）—— 压缩部分已弃用

> **2026-11-11 修订**：原本打算借它的 RTK 压缩（caveman / ponytail / autodetect / headroom）。
> Master 指出「压缩没必要交给网关」→ **压缩部分全部弃用**，只留 SSE 分层结构。

### ✅ 借什么

| 机制 | 落点 | 为什么值得借 |
|---|---|---|
| **SSE 流式分层**（`open-sse/executors` / `handlers` / `providers` / `transformer` / `translator`） | 转发层的流式处理 | 流式响应的格式翻译是最容易出错的地方，这个分层（执行器→处理器→provider→转换器→翻译器）值得照搬结构 |
| **多账号降级** | 路由层降级策略 | 同一 provider 多账号轮换，配额耗尽时切号而非切 provider |

### ❌ 弃什么

| 不借 | 理由 |
|---|---|
| **RTK 压缩全套**（`caveman` / `ponytail` / `autodetect` / `headroom` / `registry` / `filters`） | **有损操作必须有唯一负责人**。Agent 知道自己的对话结构（哪段不可恢复），网关只看到一个 messages 数组，只能按通用规则压 → 压掉的可能是 agent 特意保留的细节。且 agent 已压过一次，网关再压 → 双重有损，出问题无法归因 |
| **Next.js 全家桶 + 1544 个 js 文件** | 上游是「本地 Dashboard 优先」的形态。我们是网关，前端不是重心 |
| **`src/mitm/`** | MITM 中间人代理，与网关职责不同，且引入证书管理复杂度 |
| **「连接 Claude Code / Cursor / Copilot」的 IDE 集成** | 那是客户端适配，不是网关职责 |
| **npm 包发布形态** | 上游是 npm 包（`npx 9router`），我们按服务部署 |
| **Dashboard 的 i18n 十国语言** | 前端没做之前不谈 i18n |

**留一句在文档里防复发**：9router 的 RTK 是给「人在 Dashboard 里聊天、context 由它自己管」的场景设计的；
我们下面挂的是 Claude Code / Cursor，**它们有完整的 context 管理**。照搬卖点等于在别人管好的地方再插一手。


## 四、合起来的分层（压缩层已删）

```
       ┌──────────────────────────────────────────────────┐
请求 → │ ① 接入层（协议）   OpenAI 兼容 / Anthropic / Responses │
       │    借 one-api 的 relaymode 分流思路                 │
       └────────────────────┬─────────────────────────────┘
                            ↓
       ┌──────────────────────────────────────────────────┐
       │ （压缩层已删除 —— 见下方说明）                        │
       └────────────────────┬─────────────────────────────┘
                            ↓
       ┌──────────────────────────────────────────────────┐
       │ ③ 路由层（选谁）   健康租约 + 失败分类 + rank_targets │
       │    借 freellmpool 的 Pool 全套                     │
       │    + one-api 的 ability 能力表                      │
       └────────────────────┬─────────────────────────────┘
                            ↓
       ┌──────────────────────────────────────────────────┐
       │ ④ 转发层（适配）   38 家 provider adaptor 结构       │
       │    借 one-api 的 adaptor/interface 契约             │
       └──────────────────────────────────────────────────┘
```

**三层职责互不越界**：
- 压缩层不改路由决策（压不压不影响选谁）
- 路由层不改协议（选完直接交给适配器）
- 适配层不管健康（失败上抛给路由层记租约）

## 五、我们不从三者借、自己要做的东西

| 能力 | 为什么别人没有 |
|---|---|
| **可解释路由** | 三家都只给「结果」，不给「为什么选这条」。我们要每次返回 `route_trace`（候选集、排除原因、最终依据） |
| **成本预算硬门** | 三家都只有事后统计。我们要「预算到线就降级/拒绝」，不是超了才告警 |
| **route_trace 落盘可回放** | 出问题能按原样重放一次路由决策，用于回归 |
