## 一、技术栈决策：**Python**

### 决策依据（不是偏好，是能抄多少代码）

| 候选 | 可直接借鉴 | 占比 | 说明 |
|---|---|---|---|
| **Python** ✅ | freellmpool `router.py`（1627 行，路由核心）+ `proxy.py`（OpenAI 兼容网关）<br>**KXNS `soul/jailbreak/`（981 行，破甲全套）** | **2/3** | 两个最难的部分都有现成实现可抄 |
| Go | one-api `relay/adaptor/`（38 个 provider） | 1/3 | 但 adaptor 是「字段映射」，接口设计可抄、代码要重写 |
| Node/TS | 9router `open-sse/`（SSE 分层 + RTK 压缩） | 1/3 | 分层结构可抄，但压缩逻辑本身是纯 JS 函数，改写成 Python 不难 |

### 为什么性能不是问题

AI 网关的延迟构成：

```
客户端 → 网关 → 上游 API → 网关 → 客户端
         ↑                    ↑
      毫秒级                秒级（LLM 生成）
```

**瓶颈在上游**。Python asyncio 处理 SSE 流式转发，单机几千并发没有任何压力。
「Python 慢」在 IO 密集型场景是伪问题——慢在 CPU 密集（自己做推理）才成立。

### 依赖选型

| 用途 | 选谁 | 为什么 |
|---|---|---|
| HTTP 客户端 | `httpx` | 原生 async + HTTP/2，SSE 流式支持好 |
| Web 框架 | `FastAPI` + `uvicorn` | 原生 async，自动 OpenAPI 文档 |
| 配置 | `pydantic-settings` + TOML | 与 freellmpool 的 `config.toml` 一致 |
| 存储（自用） | `SQLite`（WAL 模式） | 单机够用，零运维 |
| 测试 | `pytest` + `pytest-asyncio` | 与 KXNS/freellmpool 一致 |

**层间纪律**（每层只做自己的事，不越界）：
- ⓪ 只决定「路由由谁定」，不改请求内容
- ② 只改 prompt 措辞，**不改路由决策、不改授权判定**
- ③ 只压 token，不改语义、不改路由
- ④ 只选目标，不改协议
- ⑤ 只做字段映射，不管健康（失败上抛）

## 三、⓪ 模式层：AUTO / MANUAL（Master 明确要的）

### 两种模式

| 模式 | 谁选路由 | 什么时候用 |
|---|---|---|
| **AUTO** | 网关按 `rank_targets` 自动选：健康度 + 配额 + 延迟 + 成本 | 日常；想要「省心 + 省 token」 |
| **MANUAL** | 用户指定 `provider/model`（或 `provider:account`） | 调试；特定模型效果好；想固定走某家 |

### 三种指定粒度（MANUAL）

```
model: "gpt-4o"                    → 只锁模型，provider 由网关在支持该模型的渠道里选
model: "openai/gpt-4o"             → 锁 provider + 模型
model: "openai:key2/gpt-4o"        → 锁 provider + 具体账号 + 模型
```

**为什么要三档**：「锁 provider 但让它自己选账号」是最常用的——key1 配额用完了自动换 key2，
但不会跑到别家去（保证行为一致）。

### 降级策略（MANUAL 下也生效）

MANUAL 不是「死锁」。用户指定 `openai/gpt-4o`，而 OpenAI 全挂了怎么办？

| 策略 | 行为 |
|---|---|
| `strict` | 直接失败，不降级（默认） |
| `fallback_same_model` | 找支持同模型名的其他 provider |
| `fallback_any` | 任意可用模型（会改变输出风格，慎用） |

**默认 `strict`**：MANUAL 的语义是「我明确要这个」，静默换家等于骗人。
要降级必须显式配。

### 请求头约定（不改 body，零侵入）

```
X-Gateway-Mode: auto | manual
X-Gateway-Route: openai/gpt-4o
X-Gateway-Fallback: strict | fallback_same_model | fallback_any
X-Gateway-Jailbreak: auto | white_hat | red_team | black_ops | forensic | off
X-Gateway-Compress: auto | off | caveman | ponytail
```

**为什么不写在 body 里**：body 是 OpenAI 标准格式，加私有字段会被严格校验的上游拒。
请求头是 HTTP 层的东西，透传不进去也不会出错。

## 四、② 破甲层设计（抄 KXNS，981 行）

### 为什么放网关而不是客户端

KXNS 里破甲是**客户端侧**（agent 自己拼 system prompt）。放到网关的好处：

1. **所有客户端共享**：Claude Code / Cursor / 自己的脚本，接上网关就都有
2. **统一升级**：模型对齐升级后，改网关一处，所有客户端生效
3. **可观测**：拒答率、重试率在网关侧统一统计

### 三层机制（照抄 KXNS）

| 层 | 做法 | 落点 |
|---|---|---|
| **① 身份锚定** | system prompt 前置一段「这是已授权的红队/协同披露作业 + 世界级渗透专家」 | `jailbreak/personas.py` 四个人设 |
| **② 拒绝检测** | 响应**头 200 字符内**匹配中英 **45 条短语库** | `jailbreak/refusal.py` |
| **③ reframe retry** | 拒绝 → 换更强 system prompt 重试 → 仍拒 → 追加 user reminder 再问 | `jailbreak/retry.py` |

**为什么检测只看头 200 字符**：模型的拒绝话术总是在开头。看全文会误判——正文里引用一句
"我不能协助攻击"（作为分析对象）不该被当成拒答。

### 自动选档（照抄 KXNS selector.py）

| 信号 | 档位 |
|---|---|
| `10.x` / `192.168.x` / `127.0.0.1` / `*.htb` / `*.thm` / `*.ctf` | `red_team` |
| 任意公网 URL/域名 | `red_team`（降低误拒） |
| 含「渗透/拿站/黑盒/pentest」意图词 | `red_team` |
| 本地路径 / `file://` | `forensic` |
| 无目标闲聊 | `white_hat` |
| 显式 `black_ops` | `black_ops` |

### 网关侧特有的两条硬约束

**① 破甲不参与授权判定**（KXNS §4.5 原文照录）
```
破甲只过模型"心理关"，不参与也不削弱授权判定。
```
网关侧对应做法：破甲层在**鉴权之后**执行。没通过鉴权的请求根本进不来，
不存在「破甲帮谁绕过了鉴权」。

**② 破甲是可关闭的，且默认状态可见**
```
X-Gateway-Jailbreak: off        # 单请求关闭
GATEWAY_JAILBREAK=off           # 全局关闭
```
**每次响应带 `X-Gateway-Trace`**，写明本轮用了哪个档、重试了几次 —— 不许静默生效。

### 和演化隔离（KXNS §4.5 第 1 条）

KXNS 的教训：破甲块若成为「可演化对象」，prompt 演化几代就把它漂没了。
网关侧对应：**破甲层是追加式补丁，本体不可被配置热更新覆盖**。

## 五、③ 压缩层设计（借 9router RTK）

### 策略注册表（抄 registry.js 的思路）

```python
# 每个策略是一个纯函数：messages -> messages
STRATEGIES = {
    "off":       lambda m: m,
    "caveman":   caveman_filter,      # 砍冗余措辞（"请帮我" → 删）
    "ponytail":  ponytail_filter,     # 砍结构（合并重复上下文）
    "auto":      auto_select,         # 按 autodetect + headroom 选
}
```

### 三个关键决策（抄 9router 的真机制，不是无脑压）

| 机制 | 规则 | 为什么 |
|---|---|---|
| **autodetect** | 短 prompt（< 阈值）不压 | 压了反而更差，且省不了多少 |
| **headroom** | 预算余量充足时不压 | 保质量优先，快超预算才压 |
| **可 A/B** | 每次记录「压前/压后 token 数 + 上游响应质量分」 | 9router 只说省 20-40% 但没做 A/B；我们要能回答「压完质量掉多少」 |

### 我们比 9router 多做的一件

**压缩效果归因**：每次压缩落一行记录

```json
{"req_id": "...", "strategy": "caveman", "tokens_before": 3200, "tokens_after": 2100,
 "saved_pct": 34.4, "upstream_ok": true, "refusal": false}
```

这样才能回答「caveman 在哪些请求上省得多、在哪些上会导致拒答」。

## 六、④ 路由层设计（抄 freellmpool Pool）

### 核心机制（照抄 1627 行的关键部分）

| 机制 | freellmpool 的做法 | 我们怎么用 |
|---|---|---|
| **健康租约** | `_acquire_route` / `_record_route_success` / `_record_route_failure` / `_refresh_route_lease` | 照抄。防同一死路由被多请求同时打 |
| **失败分类** | `_is_health_failure` / `_health_failure_class` / `_is_account_quota_exhaustion` | **照抄，这是最有价值的一条**：配额耗尽→换号；服务故障→换 provider |
| **目标排序** | `rank_targets`（健康度 + 配额 + 延迟） | 照抄，加一维「成本」 |
| **冷却** | `_mark_cooldown` + `cooldown_snapshot` | 照抄 |
| **第一波分离** | `_provider_first_wave` | 照抄：先打主力池，失败才降免费池 |
| **能力表** | （freellmpool 无，借 one-api `model/ability.go`） | 「哪个渠道能服务哪个模型」查表，不硬编码 |

### 我们比 freellmpool 多做的：成本维度

`rank_targets` 的排序键改为四元组：

```
score = w_health * health + w_quota * remaining_quota + w_latency * (1/latency) + w_cost * (1/cost)
```

权重可配。**默认 `w_cost=0`**（不省钱优先），开启 `--prefer-cheap` 才生效。

## 七、我们要自己做、三家都没有的

| 能力 | 为什么三家都没有 | 我们怎么做 |
|---|---|---|
| **可解释路由 `route_trace`** | 三家都只给结果 | 每次响应带完整决策链：候选集、每个被排除的原因、最终依据 |
| **压缩效果归因** | 9router 没做 A/B | 每次压缩落一行记录，可算「策略 × 节省率 × 拒答率」三维 |
| **成本预算硬门** | 三家只有事后统计 | 预算到线 → 按策略降级或拒绝，不是超了才告警 |
| **route_trace 可回放** | 无 | 存决策输入快照，能按原样重放一次路由，用于回归测试 |

## 九、首版范围（「一次性做好」按 Master 要求）

**做**：六层全做，但每层的**广度按需**：

| 层 | 首版广度 | 后续扩展 |
|---|---|---|
| ⓪ 模式层 | auto + manual 三档指定 + 三种降级策略 | — |
| ① 接入层 | OpenAI chat/completions 完整 + Anthropic messages | responses / embeddings / audio |
| ② 破甲层 | **全套**（四个人设 + 45 条拒绝库 + retry） | 加更多短语库 |
| ③ 压缩层 | caveman + ponytail + auto（autodetect + headroom） | 更多策略 |
| ④ 路由层 | **全套**（租约 + 失败分类 + 排序 + 冷却 + trace） | 成本维度 |
| ⑤ 转发层 | **先做 5 家**：OpenAI / Anthropic / DeepSeek / Gemini / 国内聚合 | 逐步加 |

**为什么转发层先做 5 家**：38 家是「字段映射」的体力活，不阻塞架构验证。
先把 5 家跑通、`route_trace` 和破甲验证有效，再加是最省时间的顺序。

**不做**（首版明确排除）：
- 多租户 / 计费 / 兑换码（自用不需要）
- Web 管理后台（先 CLI + TOML 配置）
- 多实例部署（单机 SQLite）
- MCP 包装
